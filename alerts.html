崩服告警与备份看护

「在线」不等于「没事」。一台 CPU 打满的服务器照样显示 running；一台从没备份过的服务器照样显示正常——直到它挂的那天。这个工具就是替你盯着这三件事：状态、负载、备份。

三步开始 
# 1. 先确认通道通不通（配置告警最常见的卡点是 webhook 地址填错）
$ pteropilot-alerts --webhook "https://..." --test

# 2. 试着跑一次（--dry-run 只演算将要通知谁，不真的发）
$ pteropilot-alerts --webhook "https://..." --cpu 85 --memory 90 --backup-days 7 --dry-run

# 2b. 磁盘快满也会静默出事：单独加 --disk
$ pteropilot-alerts --webhook "https://..." --disk 85 --dry-run

# 3. 挂到 cron，每 5 分钟看一次
*/5 * * * * pteropilot-alerts --webhook "https://..." --cpu 85 --memory 90 --disk 85 --backup-days 7

它装在 Pteropilot 旁边，装 Pteropilot 就有：pip install pteropilot 之后同时得到 pteropilot 和 pteropilot-alerts 两个命令。只读运行，不会重启、不会改文件。

三种触发

它到底在盯什么

① 状态异常

服务器离线、报错、挂起，或者日志里出现 OOM / JVM 崩溃 / 进程退出这类崩溃信号。这是默认就在管的一项。

--min-level abnormal

② 负载超限

状态是 running，但 CPU 或内存已经顶到阈值。这种「活着但快撑不住」的情况，只看在不在线的工具永远不会叫。

--cpu 85 --memory 90

--disk 85

③ 备份过期

最新成功备份比阈值还旧，或者一次都没成功过。这是最容易漏掉、代价也最大的一项——崩了你才发现上次备份是三个月前。

--backup-days 7

负载那一项：CPU 是绝对值百分比，内存是使用率（memory_bytes / memory_limit）。面板没给内存上限的服务器会跳过内存检查，而不是拿 0 当分母算出一个假百分比。等于阈值就算命中（到 85 就叫，不是超过 85）。默认 0 = 关闭。失败的备份不算备份——恢复不了的不叫备份。

别被误报淹没

告警响太多次，人就学会无视它了

冷却去重

同一台服务器、同一个状态，在冷却期内只推一次。状态真的变了（比如从「负载异常」变成「离线」）会立刻推——新故障值得马上知道。

--cooldown 60（分钟）

连续确认

连续 N 次检测到异常才推。对付那种一秒钟就恢复的抖动——它不该把你半夜叫醒。恢复正常会清零计数。

--confirm-count 2

按服务器单独设阈值 
# ~/.pteropilot/alerts.json —— 一个全局数字不可能同时适配这两种服
{
  "default": { "cpu_threshold": 85, "memory_threshold": 90, "disk_threshold": 85, "backup_days": 7 },
  "servers": {
    "heavy-pack": { "cpu_threshold": 97, "memory_threshold": 98 },
    "tiny-lobby":  { "cpu_threshold": 60, "backup_days": 2 }
  }
}

优先级：服务器条目 > default 段 > 命令行参数。四个阈值（含磁盘 disk_threshold）都能这样覆盖。这个文件里拼错一个键会被静默忽略——用 pteropilot --doctor 校验，它会指出键名并给出建议。重负载的整合包服 85% CPU 是常态，小大厅服 50% 就该看一眼——所以必须能按服务器调。这个文件里还能按服务器设 webhook 目标、收件人、冷却与确认次数。

通道与退出码

发到哪，以及脚本怎么判断

钉钉 / 企业微信 / 邮件

  • webhook 机器人：--webhook，企业微信再加 --token
  • 邮件：--smtp-host / --smtp-user / --smtp-pass / --mail-to
  • 两者可以同时用；也都能在 alerts.json 里按服务器分开配
  • --test 会发一条测试通知并报告哪个通道失败

退出码

  • 有异常服务器 → 非零（可直接接监控系统）
  • 全部健康 → 0
  • --json 输出里带 channels 与 dry_run，方便脚本判断
  • 推送失败会单独标注——「查询失败」和「告警没发出去」是两回事，后者更危险
